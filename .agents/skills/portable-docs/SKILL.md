# Portable Docs（可移植文档）

## 核心原则：解释值，不要断言值

读者的设备几乎一定和你不同。文档的责任是教读者**怎么得到自己环境里的值**，而不是"你应该看到我这个值"。

| ❌ 写死（只在作者机器上成立） | ✅ 可移植（教读者判断） |
|---|---|
| 前提：`lsusb` 能看到 `1a86:7523` 和 `cafe:0001` | `lsusb` 编号解读表（每种芯片一行），说明编号含义与例外 |
| "板子顶边引脚 TX" | "UART0 TX (GPIO43)"，注明各板丝印位置不同 |
| "用 CH340 转 USB 查看" | "用 USB 转串口适配器查看（CH340/CH341/CP210x/FT232 均可）" |

## 写作规则

1. **区分协议身份与实例身份。** 协议层标识（服务 UUID、接口名、GPIO 编号、协议版本）对所有设备相同，可以写死。实例标识（MAC、序列号、VID:PID 组合、某个具体端口号）每台设备不同，只能作为"如何识别"的方法写出来，不能作为判据。VID:PID 要看来源：芯片厂商注册的（如 CH340 的 `1a86:7523`）对所有该芯片相同；固件自定义的（如 `0xCAFE:0x0001`）只说明"在跑某份固件"，与板卡硬件无关。

2. **前提写"如何确认"，不写"必须是什么"。** 每个前提配一条确认命令和结果解读，而不是把作者环境里的输出抄进去。

3. **枚举值给解读表。** 步骤会产生多种合理结果时（不同芯片、不同系统、不同版本），列一张"看到什么 → 是什么含义"的表。只列作者那次实测的值，读者对不上号就会误判失败。

4. **变量给替换说明。** 读者需要自己填的值（端口号、路径、IP、设备地址）在附近给一句"按实际情况替换"，并说明各情形下的常见取值。

5. **覆盖常见变体。** 写完自问：换一块板、换一个适配器、换一台电脑，每一步还成立吗？不成立的步骤要么泛化，要么分支列出。

6. **实测语境单独标注，且不侵入步骤。** "2026-11-11 在 ESP32-S3 SuperMini 上实测"这样的信息放在开头一句话，帮读者判断时效。它不是步骤的一部分，读者硬件不同不代表步骤失效。

7. **具体值给出处。** 文档里出现的每个"固定值"（UUID、PID、引脚号）注明源码或命令的来源（如 `components/ble/ble.h`），读者可以自查，也方便固件改动后有人维护文档。

8. **修订他人文档时保留既有取舍。** 作者手动删过的内容不要擅自加回；泛化是在现稿基础上改，不是推倒重写。

## 自检清单

- [ ] 文档里每处 MAC、序列号、VID:PID、端口号，是"解读方法"还是"写死的判据"？
- [ ] 换一块板 / 换一个适配器 / 换一台电脑，每一步还成立吗？
- [ ] 每个写死的值都能指出源码文件或命令出处吗？
- [ ] 需要读者替换的变量都有"按实际情况替换"的提示吗？

## 与 tech-writing 的分工

tech-writing 管句子层（长度、语态、空话）。本 skill 管事实层（哪些值可以写死、哪些必须教读者获取）。写硬件与环境相关文档时两个都要过一遍。
